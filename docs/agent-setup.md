Pinpoint hands notes to a coding agent through MCP. The bridge serves MCP over HTTP at `/mcp`, on the bridge's port (default 4747). The agent needs an MCP client that speaks HTTP.

## Set up

1. Start the bridge in the app folder:

   ```bash
   dart run pinpoint:bridge
   ```

2. Run setup in the same folder:

   ```bash
   dart run pinpoint:setup           # writes the guide in .pinpoint/, prints the rest
   dart run pinpoint:setup --write   # also copies it to where each agent looks
   ```

   Setup flags:

   | Flag | What it does |
   | --- | --- |
   | `--dir <path>` | The notes folder. Default `.pinpoint`. |
   | `--port <n>` | The bridge's port. Default 4747. |
   | `--write` | Copy the guide to the agents' folders, merge the MCP entry, add the section to `CLAUDE.md` or `AGENTS.md`. |
   | `--agents <list>` | Which agents `--write` serves: `claude`, `cursor`, `vscode`, `agents`, comma separated. Default: all four. |
   | `--refresh` | Rewrite files that exist and differ. Update an existing `pinpoint` MCP entry. |
   | `--help` | Show the usage text. |

3. Connect the agent. `--write` adds the MCP entry for you. For Claude Code you can run this instead:

   ```bash
   claude mcp add --transport http pinpoint http://127.0.0.1:4747/mcp
   ```

## What setup writes

Always, in `.pinpoint/`:

- `README.md`: what the folder is, which files are data (private), how to refresh.
- `SKILL.md`: how an agent works with Pinpoint. It has the note lifecycle, undo, how to investigate, privacy, and what not to do.
- `commands/`: `pinpoint-fix-notes.md`, `pinpoint-check.md` and `pinpoint-state.md`. Each is short and points to `SKILL.md`.
- `tools.md`: every MCP tool with its inputs. It is made from the definitions the bridge serves.
- `mcp.json`: the MCP entry, in the Claude Code form.
- `agent-instructions.md`: a section for your agent file. It starts with the heading `## Pinpoint notes`. Setup writes it again on every run.
- `.gitignore` with `*`, if it is not there yet. Everything in `.pinpoint/` stays out of git.

Each generated file has a line `generated by dart run pinpoint:setup <version>`. The bridge writes `config.json` itself. See [the bridge](bridge.md).

With `--write`, setup also copies the guide where each agent looks. The files in `.pinpoint/` stay the master copy. The copies are real files, not links.

| Agent (`--agents`) | Files |
| --- | --- |
| Claude Code (`claude`) | `.claude/skills/pinpoint/SKILL.md`, `.claude/commands/pinpoint-*.md`, `.mcp.json` (key `mcpServers`, with `"type": "http"`), the section in `CLAUDE.md` |
| Cursor (`cursor`) | `.cursor/rules/pinpoint.mdc` (not always on: the agent loads it by its description), `.cursor/mcp.json` (key `mcpServers`, only `url`) |
| VS Code (`vscode`) | `.vscode/mcp.json` (key `servers`, with `"type": "http"`) |
| Generic (`agents`) | the section in `AGENTS.md` |

The section goes to `CLAUDE.md`. If only `AGENTS.md` exists, it goes there. With only `--agents agents`, it goes to `AGENTS.md`. It is not added twice.

The MCP files are merged. Other servers and keys stay. Setup adds `pinpoint` if it is missing. An existing `pinpoint` entry stays as it is, unless you run with `--refresh`. If a file is not valid JSON, setup does not touch it. It says why, goes on with the other files, and exits with an error.

How setup treats a file that is already there: if it is the same as the new text, nothing happens. If it differs (you edited it, or it is from an older version), setup keeps it and says "kept". `--refresh` rewrites it. Setup does not compare with older generated text, so an edit and an old version look the same. After you update the package, run `dart run pinpoint:setup --write --refresh`. The bridge tells you when the guide is older: "agent guide files are from 0.0.0; run dart run pinpoint:setup --refresh".

The skill and the section use the same sentences as the MCP `instructions`. They tell the agent where notes live and how to work them. Read the files setup wrote to see the current wording.

If your agent file does not have the section yet, the bridge prints it at start.

## The note lifecycle

1. You send a note. Its status is **submitted**.
2. The agent sets it to **inProgress**, changes the code, and runs `flutter analyze`.
3. The agent sets it to **fixed** (or **resolved**, or **rejected**) with `update_note` and a one-line message.
4. The pin in the app updates. You accept the result, or you reopen the note with a reason.
5. After a reopen, the note is **submitted** again. It shows "reopened" and your reason is the last reply. The agent works it again and sets it fixed again.

`resolved` and `rejected` move the note's files to `.pinpoint/resolved/`. `fixed` keeps them in `open/`. When you accept, the note is closed and its files are in `resolved/`.

The agent should set `fixed` or `resolved` after every code change for a note, also when you asked for it in chat. The pin shows only what `update_note` says.

An agent without MCP can use the file inbox: read `.pinpoint/open/*.md`, and move a note's files (`.md`, `.json`, `.png`) to `.pinpoint/resolved/` when done. The bridge notices the move.

## Reading notes

- `list_notes` lists open notes (submitted, inProgress, fixed) by default. Drafts are never listed.
- `get_note` gives one note. At `standard` detail (the default) it adds layout, enclosing widgets and the screenshot (at most 800 px wide). `compact` gives the comment, source and rect. `full` adds properties, subtree, state owners and environment.

## Agent control

Many tools operate the running app. They need "Allow agent control" in the app. It is a button on the rail. It is off at every start. A chip shows while it is on. Esc turns it off. Set `PinPointConfig(allowAgentControl: false)` to hide it. Then no command ever reaches the app.

`hot_reload` works with agent control off. It needs the app's debug service address. Start the app with `--vmservice-out-file=.pinpoint/vm-service.txt`, or give the agent the address from the `flutter run` output once.

## Undo

The agent labels its changes. You can undo some of them. See [undo](undo.md).
